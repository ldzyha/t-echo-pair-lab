# L1: останній стан без архіву переписки

## Що залишається на T-Echo Plus

| Дані | Політика |
| --- | --- |
| Сторінка повідомлень | Один останній текст; наступний замінює попередній. Локальний лічильник непрочитаного: 0 або 1. |
| Постійний вхідний inbox пари | Одне останнє прийняте повідомлення з оригінальним ID. Після API-підключення телефон може отримати його повторно. |
| Недоставлені вихідні повідомлення | До 8 записів до захищеної квитанції або явного скасування. Зменшення історії не видаляє цю чергу. |
| Захист від повторів | Числові позначки отриманих послідовностей; тексти витіснених повідомлень не потрібні для дедуплікації. |
| Позиція партнера | Остання відома точка та її час; журнал маршруту не створюється. |
| Стан зв’язку | Останній реальний RX у поточному сеансі та його вік. Перезапуск не робить давній запис доказом нового зв’язку. |

У `MessageStore.h` типовий `MESSAGE_HISTORY_LIMIT` для Plus зменшено до 1. Якщо явно перевизначити цей параметр у власній збірці, ліміт екрана зміниться; inbox пари у L1 залишається однозаписним. Інші плати зберігають попередні типові ліміти.

Історія, уже записана Android/iOS, керується самим застосунком. Звичайні тимчасові черги API також можуть передати ще не прочитані клієнтом пакети; L1 обмежує постійне сховище, а не скасовує обмін під час підключення. Кожне живе вхідне повідомлення надходить підключеному телефону як і раніше.

## Перехід зі старої прошивки

- Старий inbox до 20 записів читається повністю і перевіряється. У новому стані залишається найновіший. Навіть запис, який буде витіснено, повинен пройти перевірку формату та адресата.
- Вихідні тексти, їхні ID, порядкові номери, ключі адресата, epoch і позначки дедуплікації переносяться без змін.
- Обидва слоти постійної черги переписуються послідовно з перевіркою читання. Поки новий слот не записаний, попередній справний слот лишається джерелом відновлення. Незавершене скорочення повторюється при наступному запуску.
- Файл повідомлень екрана також читається до кінця з обмеженою RAM-чергою. Завантажується останній повний запис, а не перший запис старого файлу.
- Подальший повтор старого радіопакета підтверджується, але не повертається як новий текст.

Це політика утримання даних, а не криптографічне стирання flash. Два службові слоти містять поточний і попередній знімок для відновлення після збою живлення. Резервні копії на комп’ютері та давній формат `.msgs`, якщо такий існує, не є активною історією L1.

## Код

- `src/MessageStore.h`, `src/MessageStore.cpp`: один текст для екрана і читання старих файлів.
- `src/modules/DeliveryQueueModule.cpp`: один вхідний запис, сумісна міграція, вихідна черга та квитанції.
- `src/mesh/DeliveryQueue.h`: курсор одного останнього повідомлення для API-клієнта.

Протокол радіообміну, сердечка H3, калібрування TH6 і налаштування позиції не змінені.

## Перевірки

17 host suites пройшли. Новий тест компілює фактичний `MessageStore.cpp` з підставленим файловим інтерфейсом: перевіряє міграцію 20 → 1, UTF-8, частковий останній запис, старий формат і локальне прочитання. Production-тести черги перевіряють збереження всіх 8 вихідних повідомлень, некоректний старий запис, збій запису, незавершену міграцію, дедуплікацію та повторне підключення.

Embedded-збірка `t-echo-plus -t mtjson` успішна. L1 встановлено на обидві фізичні рації через application-only DFU.

- Radio A: 20 → 1 вхідний запис; Radio B: 12 → 1. Звірено оригінальний ID найновішого повідомлення.
- Повна конфігурація та ключі обох пристроїв збігаються з копіями перед оновленням.
- По два нові повідомлення в кожному напрямку, включно із 187-байтним сердечком H3: точний текст отримано, захищену квитанцію підтверджено.
- По два нові USB/API-підключення до кожного пристрою: один останній запис з тим самим ID, без дублювання; вихідна черга порожня.
- Понад 100 секунд спостереження за кожною рацією без неочікуваних перезапусків. Виміряна вільна heap-пам’ять: приблизно 28–31 КБ; у попередній перевірці H3 було близько 8 КБ. Це окремі сеанси з різним поточним навантаженням.

Перед встановленням фізичні вихідні черги були порожні; перенесення заповненої черги перевірене host-тестом. Вигляд і поведінку конкретного Android/iOS застосунку цей USB/API-тест не підтверджує.
